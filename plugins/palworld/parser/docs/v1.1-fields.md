# Palworld v1.1 field locations

This spike is pinned to the committed build-24467282 fixture
`1FCE97C34D214643B96A23A20A9E27D1` and the committed
`live-20260731` fixture. Both have one player save, for player UID
`00000000-0000-0000-0000-000000000001`. The integration test
`tests/v11_fields_test.rs` decodes both through the existing PlM1/Kraken/GVAS
pipeline, then performs the same character-map/container joins as
`sections.rs`.

## Verified fields

### Player position

- Source: each `Players/*.sav` file.
- Exact property path: `SaveData.LastTransform.Translation`.
- Existing decode: `uesave::Property::Struct(StructValue::Vector)`, reached
  through the already-decoded `LastTransform` struct. No new RawData codec or
  type hint is required.
- Encoding: UE `Vector`, three little-endian IEEE-754 `f64` values in X, Y, Z
  order (24 payload bytes).
- Units and frame: absolute Unreal world coordinates in Unreal Units; one UU
  is one centimetre. No origin shift, scaling, axis swap, or other transform
  is needed. Preserve the three doubles as saved.
- Pinned values:

  | fixture | X | Y | Z |
  | --- | ---: | ---: | ---: |
  | `1FCE…` | -346946.95917404373 | 191651.84791294907 | -211.4045001832311 |
  | `live-20260731` | -351879.20256971574 | 201841.4198500383 | 1731.0433408787007 |

`Level.sav` was also checked. The player's
`worldSaveData.CharacterSaveParameterMap` value contains character state but
does not contain `LastTransform` or a current-location equivalent. Fields such
as `LastJumpedLocation` in character SaveParameter data are event/history
state and are not the player's current position. Therefore the authoritative
source for this parser is the per-player save.

Risk: `LastTransform` is last-persisted state, not a live actor transform. A
save missing that property (for example, an incomplete/new player save) must
yield a missing position rather than a fabricated `(0, 0, 0)`. Neither pinned
fixture exhibits the missing case.

### Pal sex

- Source: `Level.sav` character map value RawData.
- Hint-convention property path to the bytes:
  `worldSaveData.CharacterSaveParameterMap.RawData`. There is deliberately no
  intermediate `.Value`; map-entry fields resume directly below the map name,
  per `gvas.rs`'s path convention.
- Path inside decoded RawData:
  `SaveParameter.Gender`. `decode_character_save_parameter` unwraps
  `SaveParameter`, so the existing Rust representation is
  `CharacterSaveParameter.object` containing `PalProperty { name: "Gender",
  value: PalValue::Enum { enum_type, value }, .. }`.
- Encoding: a tagged `EnumProperty`. Both enum type and value are FString
  labels, not numeric ordinals. The bytes decode as enum type
  `EPalGenderType` and values `EPalGenderType::Female` or
  `EPalGenderType::Male`.
- Fixture proof: in party plus storage on both fixtures, `ChickenPal` decodes
  as `EPalGenderType::Female` and `PinkCat` decodes as
  `EPalGenderType::Male`; both enum values occur in each fixture.

The parser emits this data under the JSON name `sex` via `Pal.sex` and
`build_pal`. Although the raw decode retains the qualified UE labels above,
the emitted values are bare `Female` or `Male`: the field name already
identifies the enum type, so carrying `EPalGenderType::` is redundant. No
codec work is needed.

### Stable pal instance ID

- Canonical source and exact path:
  `worldSaveData.CharacterSaveParameterMap.InstanceId`, inside each map key.
  Again, there is no intermediate `.Key` in a nested field path. The terminal
  hint that types the whole key remains
  `worldSaveData.CharacterSaveParameterMap.Key`.
- Existing decode: `sections.rs::character_key` reads the key's `InstanceId`
  as `uesave::FGuid`. `decode_characters` already keys its character HashMap by
  this GUID.
- Join copies: occupied party/storage slots carry the same ID in the first
  32 bytes of
  `worldSaveData.CharacterContainerSaveData.Slots.RawData`: 16 bytes of
  player UID followed by 16 bytes of instance ID. The existing
  `CharacterContainerSlot.instance_id: [u8; 16]` decodes it.
- Encoding: UE GUID wire order, four little-endian `u32` words. Use the
  existing `FGuid::to_string()` canonical rendering.
- Pinned evidence: the first party pal is
  `719954a8-47f3-d347-6393-1084f7eb5122` in both fixture snapshots. Each
  fixture has 3 occupied party slots and 28 occupied storage slots; all 31
  instance IDs are unique across the union and every one resolves to exactly
  one character-map entry.

This is the stable per-pal identity to expose. Species, nickname, slot index,
and container ID are not identities and can change or collide.

### Owner player ID

- Source and hint-convention path to RawData:
  `worldSaveData.CharacterSaveParameterMap.RawData`.
- Path inside decoded RawData: `SaveParameter.OwnerPlayerUId`; after the
  existing wrapper removal this is `CharacterSaveParameter.object` field
  `OwnerPlayerUId`, represented as `PalValue::Guid([u8; 16])`.
- Encoding: the same 16-byte UE GUID layout (four little-endian `u32` words).
  `sections.rs::guid_bytes_to_fguid` already performs the correct conversion.
- Pinned evidence: an owned party pal's value is
  `00000000-0000-0000-0000-000000000001` in both fixtures, exactly matching
  `SaveData.PlayerUId` in that fixture's player save. The test also verifies
  that every occupied party/storage slot's leading player UID matches the
  host UID.

`OwnerPlayerUId` is optional in real character entries: some unowned/world
pals in these Level saves lack it. Do not substitute the character-map key's
`PlayerUId` or a zero GUID when the SaveParameter field is absent. For owned
pals, resolve the GUID against the set of decoded `Players/*.sav`
`SaveData.PlayerUId` values. Multiplayer saves have one `Players/<uid>.sav`
per player; party and storage container IDs are read from each corresponding
player save, so sections must retain player association instead of assuming a
single host.

## v1.1 section changes

No production-format guessing remains:

- `players.players[]`: add a nullable `position` object (recommended shape
  `{ "x": f64, "y": f64, "z": f64 }`) populated from that player's
  `SaveData.LastTransform.Translation`.
- `pals_party.pals[]` and `pals_storage.pals[]`: add `sex` from `Gender`,
  `instanceId` from the joined character-map key/container slot, and
  `ownerPlayerUId` from `OwnerPlayerUId` (the last field already exists in the
  current `Pal` output).
- Carry the instance ID into `build_pal` instead of discarding the HashMap key
  after the join. The needed-ID-set optimization remains valid: all party and
  storage slot IDs are already collected before RawData decode.
- Build each player's party/storage list from that player's container IDs, as
  today. In multiplayer, concatenate results only after retaining
  `ownerPlayerUId`; never assign every pal to the host merely because the
  current fixtures contain one player.

The paths above intentionally follow uesave's flattened map scope. A future
hint for a nested map-entry field must not introduce intermediate `.Value` or
`.Key` components.
