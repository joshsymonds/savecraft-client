# Palworld v1.2 base-detail field locations

This spike is pinned to the committed build-24467282 fixture
`1FCE97C34D214643B96A23A20A9E27D1` and the committed
`live-20260731` fixture. The integration test `tests/v12_fields_test.rs`
decodes both through the production PlM1/Kraken/GVAS pipeline and asserts
every CONFIRMED statement below. Offset ranges are half-open and relative to
the named RawData byte array.

uesave hint paths below intentionally omit synthetic `.Value` and `.Key`
segments. Map-entry fields resume directly beneath the collection name, as
documented by `gvas.rs`.

## Verified fields

### Base identity and direct payloads

- Source: `Level.sav`.
- Exact property paths:
  `worldSaveData.BaseCampSaveData.Key`,
  `worldSaveData.BaseCampSaveData.RawData`,
  `worldSaveData.BaseCampSaveData.WorkerDirector.RawData`, and
  `worldSaveData.BaseCampSaveData.WorkCollection.RawData`.
- Existing decode: `BaseCampSaveData` is a plain GVAS `Map`; its key is a
  hinted `Guid`, and its value is a hinted `Struct` containing nested GVAS
  properties. The three named leaves are GVAS byte arrays. No codec currently
  decodes them; `sections.rs::decode_base_ids` reads only the map key.
- Encoding: the map key is a UE GUID. Each of the three RawData blobs begins
  at offset `0` with the same 16-byte GUID in four-little-endian-`u32` wire
  order. `WorkCollection.RawData[16..20]` is a little-endian `u32` count. No
  meaning is assigned beyond the byte boundaries explicitly confirmed below.
- Pinned values:

  | fixture | entries | base GUID | base RawData bytes | WorkerDirector bytes | WorkCollection bytes | count at 16 |
  | --- | ---: | --- | ---: | ---: | ---: | ---: |
  | `1FCE…` | 1 | `4e18f078-4717-eb0a-043c-01b96f527fff` | 257 | 118 | 584 | 35 |
  | `live-20260731` | 1 | `4e18f078-4717-eb0a-043c-01b96f527fff` | 257 | 118 | 568 | 34 |

Verification stops after the base-id prefixes and count. The remainder of
all three blobs is opaque except for the worker-container reference below.

### Base worker container and assigned Pals

- Source: the base's `WorkerDirector` plus the referenced character container.
- Exact property paths:
  `worldSaveData.BaseCampSaveData.WorkerDirector.RawData`,
  `worldSaveData.CharacterContainerSaveData.ID`, and
  `worldSaveData.CharacterContainerSaveData.Slots.RawData`.
- Existing decode: the container map is a plain GVAS map/struct tree;
  `decode_character_container_slot` decodes the first 32 bytes of each
  occupied slot as player UID plus Pal instance ID and keeps the final six
  bytes opaque.
- Encoding and offsets: `WorkerDirector.RawData[98..114]` is the UE GUID
  `b7a83998-4821-1a8a-db54-42991e05b929`; `[114..118]` is four zero bytes.
  That GUID resolves to a character container with five occupied slots in
  each fixture.
- Pinned values:

### Work assignments and machine state signal

- Source: `WorkSaveData` and the base-linked `MonsterFarm` map object.
- Exact property paths:
  `worldSaveData.WorkSaveData.WorkableType`,
  `worldSaveData.WorkSaveData.RawData`,
  `worldSaveData.WorkSaveData.WorkAssignMap.RawData`, and
  `worldSaveData.MapObjectSaveData.ConcreteModel.ModuleMap.RawData` for the
  `EPalMapObjectConcreteModelModuleType::Workee` entry.
- Existing decode: `WorkSaveData` is a plain GVAS struct array;
  `WorkableType` is a GVAS Enum and `WorkAssignMap` is a GVAS map with Int
  keys and hinted Struct values. Both the work record and assignment value
  carry RawData byte arrays.
- Encoding and offsets: every work record begins with a 16-byte work GUID.
  An assignment blob is 62 bytes: `[0..16]` repeats its parent work GUID,
  `[37..53]` is an assigned Pal instance GUID, and `[53..62]` is exactly
  `02 01 00 00 00 00 00 00 00`. All other assignment bytes are opaque. The
  base `MonsterFarm` has a Workee module whose first 16 bytes equal the work
  record with plain-GVAS state signal
  `EPalWorkableType::MonsterFarm`.
- Pinned values:

  | fixture | work records | assignment keys | assigned Pal IDs | machine signal |
  | --- | ---: | --- | --- | --- |
  | `1FCE…` | 8 | `0`, `0`, `0` | `8fd0a461-4b36-96d9-592e-99bee9ca4953`, `c63b3553-49f9-f3f5-1aee-e498828c41ad`, `36d42d72-4589-a111-073f-50a0556e6866` | base `MonsterFarm` → Workee GUID → `EPalWorkableType::MonsterFarm` |
  | `live-20260731` | 8 | `0`, `0`, `0` | same three IDs | same join and enum |

The unlisted ranges of each 62-byte assignment and everything after the work
record's initial GUID remain opaque.

### Build-process bytes

- Source and exact path:
  `worldSaveData.MapObjectSaveData.Model.BuildProcess.RawData`.
- Existing decode: BuildProcess is a nested plain GVAS Struct carrying a byte
  array; there is no RawData codec.
- Encoding: UNCONFIRMED. Every base-linked object in both fixtures has the
  exact same 21 bytes,
  `01 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00`.
  The bytes themselves and their 21-byte boundary are CONFIRMED, but no bit
  or field is labelled because neither fixture supplies a contrasting state.
- Pinned values:

  | fixture | base-linked objects | distinct BuildProcess byte values | under-construction example |
  | --- | ---: | ---: | --- |
  | `1FCE…` | 37 | 1 (the value above) | absent |
  | `live-20260731` | 36 | 1 (the value above) | absent |

Verification stops at the observation of the exact bytes. In particular,
calling the first byte `is_built` or a progress flag would be a guess.

## Upstream hypotheses

The comparison target is cheahjs/palworld-save-tools (`rawdata/base_camp.py`,
`rawdata/map_object.py`, and `rawdata/work.py`, git main), the same upstream
family cited by the working codecs in `src/rawdata/`.

- **CONFIRMED:** GUIDs use the four-little-endian-`u32` UE representation at
  the offsets explicitly pinned above.
- **CONFIRMED:** item-slot and character-container-slot prefixes already
  implemented in this parser decode and cross-join against both fixtures;
  their existing trailing-byte boundaries remain intact.
- **UNCONFIRMED:** a complete upstream `BaseCampSaveData`, WorkerDirector, or
  WorkCollection layout. Only the isolated fields above are verified.
- **UNCONFIRMED:** meanings for the other bytes in MapObject Model,
  ConcreteModel modules, Work records, or WorkAssign values.
- **UNCONFIRMED:** every semantic interpretation of BuildProcess RawData,
  including any upstream construction-progress or completion flag.

No upstream layout is suitable for a codec in this build without additional
contrasting fixtures. This follows the precedent in `src/rawdata/group.rs`,
where porting an unverified upstream suffix produced impossible array counts
in the tens of millions.

## Confirmed byte cost per base

This is a conservative count of bytes whose field meaning is confirmed by the
test, not the size of the opaque carrier blobs and not a proposed JSON shape.
It counts each confirmed occurrence used by the joins: base key/prefixes and
count (68 bytes), worker reference/trailer and five 32-byte slot prefixes (180),
16-byte base links plus exact 21-byte BuildProcess payloads per base object,
the chest container reference (16), decoded non-trailing item-slot bytes
(390), eight work-ID prefixes (128), three confirmed assignment ranges
(123), and the MonsterFarm Workee link (16).

| fixture | confirmed bytes | section budget | headroom before JSON/NDJSON overhead |
| --- | ---: | ---: | ---: |

Opaque bytes are deliberately excluded because emitting them is not part of
the epic. This arithmetic is a feasibility input only; the eventual emitted

## Gate

**NO-GO.** The build cannot be declared capable of all four required
relationships from these committed real saves:

- Stocked item container: **exhibited.** The base-linked `ItemChest` joins to
  the eight-slot stocked container and exact item counts above.
- Assigned worker Pal: **exhibited.** Three WorkAssign Pal GUIDs join to the
  base's five-Pal worker container in both fixtures.
- Machine or building with readable state signal: **exhibited.** The
  base-linked `MonsterFarm` Workee GUID joins to a work record whose plain
  GVAS enum is `EPalWorkableType::MonsterFarm` in both fixtures.
- Building under construction: **not exhibited.** All 37 base objects in
  `1FCE…` and all 36 in `live-20260731` carry the identical 21-byte
  BuildProcess payload. There is no contrasting under-construction instance,
  so its encoding and expected progress/state values cannot be verified.

REQ-19 therefore stops the epic for an explicit owner scope/fixture decision;
there is no implicit verified-subset fallback.
