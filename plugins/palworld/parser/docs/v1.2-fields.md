# Palworld v1.2 base-detail field locations

This spike is pinned to the committed build-24467282 fixture
`1FCE97C34D214643B96A23A20A9E27D1` and the committed
`live-20260731` fixture. The integration test `tests/v12_fields_test.rs`
decodes both through the production PlM1/Kraken/GVAS pipeline and asserts
every CONFIRMED statement below. Offset ranges are half-open and relative to
the named RawData byte array.

uesave hint paths below intentionally omit synthetic `.Value` and `.Key`
segments. Map-entry fields resume directly beneath the collection name, as
documented by `gvas.rs`.

### Base position and name

- Source and exact path: `worldSaveData.BaseCampSaveData.RawData`, joined to
  the base-linked `PalBoxV2` at
  `worldSaveData.MapObjectSaveData.Model.RawData`.
- Position encoding: `BaseCampSaveData.RawData[89..113]` is three
  little-endian IEEE-754 `f64` values in X, Y, Z order. It is byte-identical
  to the base-linked `PalBoxV2` model's `[104..128]` transform translation in
  both fixtures. The PalBox model is independently linked to the base by its
  GUID at `[32..48]`; this is not a shape-only identification.
- Pinned position in both fixtures: `(-347922.1286995581,
  264690.7242905643, 4006.8075977033227)`. The two complete 257-byte base
  blobs are byte-identical, providing the required cross-fixture agreement.
- Anchor checks: the position is 73,167 UU from the pinned `1FCE…` player
  position and 63,015 UU from the pinned `live-20260731` player position.
  Paldata's existing Readout (`scale = 459`, `originX = -123888`,
  `originY = 158000`) projects it to approximately `(232.442, 488.092)`,
  inside the 0–1000 map bounds and on the same land location as the PalBox.
  The transform is consumed as documented by paldata, not re-derived here.
- Name encoding: `[16..20]` is signed FString length `-18`; `[20..54]` is
  17 UTF-16LE code units and `[54..56]` is its null terminator. Both fixtures
  decode exactly to `新規生成拠点テンプレート名0(仮)`. This appears to be an
  internal/default template name, but the saved string itself is CONFIRMED;
  no friendlier display-name interpretation is claimed.
- Level: **UNCONFIRMED.** `[56..60]` is `01 00 00 00` in both fixtures and is
  adjacent to the FString, but there is no contrasting level or independent
  plain-GVAS anchor. Calling it level 1 would violate the cross-fixture
  verification rule.

Candidate scanning did not supply an alternative position. Testing every
byte offset of the 257-byte base blob for three finite, map-scale f64 values
found only offset 89 with substantial X and Y coordinates. Its exact PalBox
translation match confirms it; candidates in the base-linked model blobs all
occur at offset 104 and locate their individual objects around that PalBox.
No plain-GVAS transform property exists on these map-object entries: the
transform is carried by `Model.RawData`.

## Upstream hypotheses

The comparison target is cheahjs/palworld-save-tools (`rawdata/base_camp.py`,
`rawdata/map_object.py`, and `rawdata/work.py`, git main), the same upstream
family cited by the working codecs in `src/rawdata/`.

- **CONFIRMED:** GUIDs use the four-little-endian-`u32` UE representation at
  the offsets explicitly pinned above.
- **CONFIRMED:** the isolated base position and name encodings above, including
  the byte-for-byte join to the independently base-linked PalBox transform.
- **CONFIRMED:** item-slot and character-container-slot prefixes already
  implemented in this parser decode and cross-join against both fixtures;
  their existing trailing-byte boundaries remain intact.
- **UNCONFIRMED:** a complete upstream `BaseCampSaveData`, WorkerDirector, or
  WorkCollection layout. Only the isolated fields above are verified.
- **UNCONFIRMED:** meanings for the other bytes in MapObject Model,
  ConcreteModel modules, Work records, or WorkAssign values.
- **UNCONFIRMED:** every semantic interpretation of BuildProcess RawData,
  including any upstream construction-progress or completion flag.
- **UNCONFIRMED:** base level. The identical adjacent value `01 00 00 00`
  cannot establish a semantic field without a contrasting fixture or anchor.

No upstream layout is suitable for a codec in this build without additional
contrasting fixtures. This follows the precedent in `src/rawdata/group.rs`,
where porting an unverified upstream suffix produced impossible array counts
in the tens of millions.

## Parser output confirmation

The parser's `bases` section now emits the confirmed base ID, saved FString,
position, WorkerDirector container occupants, and map-object aggregation by
verbatim `MapObjectId`. Item totals are aggregated from base-linked
`ItemContainer` modules. Base level and guild attribution are not emitted.
Items are trimmed by lowest quantity until the serialized bases section is at
most 81,920 UTF-8 bytes, recording omitted type and quantity totals in
`trimmed`.

### Why the field is `mapObjects`, not `buildings`

The aggregation is emitted as `bases[].mapObjects[]`, keyed by the verbatim
`MapObjectId`, because that is what the set actually contains. All 36
base-linked objects in `live-20260731` are genuinely base-linked — each
one's `Model.RawData[32..48]` equals the base GUID — but 14 of them are
`CommonDropItem3D` (dropped item pickups) and two are `DamagableRock0009` /
`DamagableRock0012` (world rocks): 39% of the field is loot on the floor and
scenery, not player-built structures.

Nothing in the save distinguishes a built structure from a world object, so
the parser does not attempt the classification and does not filter the set.
That classification lives cloud-side, where `DT_BuildObjectDataTable` (498
real buildings) is joined on `MapObjectId` to identify and name the entries a
player would recognize as buildings. The parser's contract is the honest
superset plus the exact id; naming and filtering are the cloud's.

### Flag typing and the `unknown` tally

Every value of `mapObjects[].flags` is one JSON type family, `number|null`:

- A number is a tally of objects in that entry carrying the condition.
- `null` means the flag exists but this build can source no signal for it at
  all. `powered` and `damaged` are null because no signal is confirmed;
  `under_construction` is null because the identical BuildProcess payload
  does not establish a condition. A string sentinel in an integer field is
  forbidden — a consumer must not have to special-case a key's type.

`working` is the only sourceable flag: it tallies objects whose Workee link
resolves to a `WorkSaveData` record with a readable `WorkableType`.

`unknown` is not a peer flag. It counts the objects for which NO condition
signal of any kind was readable, so it is mutually exclusive with every
sourceable flag — an object with a work signal is never also counted unknown.
Sourceable tallies may still overlap each other (REQ-9: an object can be both
powered and damaged), so the invariant is: `unknown` plus the number of
objects carrying at least one sourceable signal equals `count`. With
`working` as the only sourceable flag this reduces to
`unknown + working == count`, asserted over real parser output by
`tests/pipeline_test.rs`.

**NO-GO.** The build cannot be declared capable of all four required

- Stocked item container: **exhibited.** The base-linked `ItemChest` joins to

- Assigned worker Pal: **exhibited.** Three WorkAssign Pal GUIDs join to the

- Machine or building with readable state signal: **exhibited.** The
